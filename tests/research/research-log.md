## 2026-09-23 (engine fixes from the LLM experiment: pushbutton landing, interchangeable button groups, final_check no longer mixes in history; orientation lock tried and reverted)

**Fixes (user: "fix it"):**

Note: this is the same pair list the 09-22 entry removed, but with a different meaning. That contradicted the rule "final_check never trusts history". It now passes an empty history at final_check; real shorts on the finished board are still caught (regression test).

**Tried and reverted: an orientation lock** (remember which way round each symmetric part was committed; later steps must match). A third version relabelled legs by the breadboard strip they were placed in (sound in principle), but broke ~30 tests whose later steps use stand-in columns that don't match the landing's. All reverted. Position-based identity for symmetric legs stays open (as flagged on 2026-09-22).

## 2026-09-23 (supervisor feedback → generalisation brainstorm → first LLM lesson-generation experiment)

**Trigger:** supervisor's view that, from a business perspective, Arduino/robotics is a small target group; asked whether the platform could generalise to furniture building, fixing things, Arduino and robotics. Worked out in discussion (brainstorm only, no design decisions locked), then one concrete experiment built in a **copy of the project** (`~/Desktop/AR Project - LLM lesson experiment`, git branch `llm-lesson-gen`), leaving the original untouched.

**Brainstorm conclusions (not yet decisions):**
- **Don't widen the research question.** The defensible core is still exact, hole-level verification on a fixed known grid; "fix anything" re-enters the crowded space already rejected in README §1.1 (iFixit FixBot). Answer the business concern with a **platform framing** instead: Arduino is the entry point because it's the one domain where exact checking is solvable and uncontested today.
- **A bigger market without generalising:** sell to schools, universities, vocational training (B2B), not just hobbyists.
- **LLM-authored answer keys:** the engine already works on a graph (parts → named pins → connections) and never needs to know what an Arduino *is*. An LLM could turn any instructions into that graph. Candidate second research question: *can an LLM turn assembly instructions into a checkable connection graph, and how accurate is it against hand-made ones?*
- **General graph format** needs: parts, ports (capability tags + how many connections each takes), connections with a **mode**: electrical connections are transitive (A–B, B–C ⇒ A–C, current checker), mechanical ones are per-joint (A bolted to B and B to C ≠ A attached to C). Plus constraints (order, orientation), groups (interchangeable parts, sub-assemblies) and state checks ("does the drawer slide", "does the LED light"). Scope honestly as *anything assembled from discrete parts*, not fabrication (cutting, gluing, soldering quality).
- **Hard parts flagged:** interchangeable parts don't scale in the current checker (`symmetric_variants` tries every combination; a table with 4 identical legs and 16 identical holes would need real graph matching). Joints hidden once the back panel is on need per-step confirmation, which `confirmed_pairs` already does. Fixing ≠ building: a repair is a diff between two graphs (current → target) with *disconnect* steps, whereas the engine currently assumes you start from an empty board.
- **Plugin architecture** if it's ever built: a domain-neutral core plus plugins (electronics, mechanical…) declared by the lesson's `profiles` list; each connection routed to exactly one plugin by its `kind`; fixed combination rules (validation = all must pass; substitution = strictest wins; safety = any block stops the step), so combining plugins can never loosen either one. Most of the electronics plugin already exists inside `engine.py` (`checker.check`, `_try_pin_substitution`, `_cross_step_short`, `_adjusted_code`). Safety should also be worked out from the parts (e.g. a mains-voltage card), not trusted from an LLM-assigned lesson label alone.
- **Gap found while brainstorming (real, not fixed):** the engine has no notion of PWM (`grep -i pwm core/` finds nothing). Harmless for the three built lessons, but Fade (`analogWrite`) and any motor-speed lesson would accept a substitution onto a non-PWM pin and silently do nothing. Needs capability tags (`pwm`, `interrupt`, `i2c`, `spi`) on board pins.
- **Chatbot idea:** instead of a stored lesson library, "tell us what you're building", classify → load the domain plugins → the LLM generates a one-off graph + steps under a JSON schema → validate → repair loop → the user confirms → the engine runs it. How reliable this is depends mostly on whether there's a real source to work from (manual/tutorial) vs. the LLM's general knowledge.

**Experiment built: LLM lesson generation, electronics only, current format.** Full write-up: `experiments/llm-lesson-gen/README.md`.
- Sources: the three docs.arduino.cc Basics pages saved locally (text from each page's Gatsby `page-data.json`, circuit + schematic PNGs, official sketch from `arduino/arduino-examples`, since the page only embeds it).
- Generator: Claude Sonnet as a fresh agent, reading only `GENERATOR_BRIEF.md`, its tutorial sources and `library_index.json`; told not to read the project's hand-made answer keys (instruction only, not enforced). One attempt, no repair loop.
- Scorer (`evaluate.py`): structure, library ids, pin names, internal consistency, code ↔ circuit, **equivalence as the headline** (graph isomorphism: pin choice and instance names ignored, per the user's direction that pin 12 vs 13 doesn't matter; board pins compared by kind), exact pins (informational), and a real-engine end-to-end run with the reference's physical wiring shown at `final_check`.

Two scorer bugs fixed along the way (literal instance-id comparison `bb2` vs `bb1`; an engine pin substitution counted as a failure).

Blink ✅ same; used 220 Ω (the tutorial's value, where the reference uses 1 kΩ), omitted the USB cable, LED placed before the resistor. A convention the brief never stated (and arguably an engine limitation, since four legs in four columns is physically correct), not a circuit error. **Run 1: 3/3 circuits correct; 2/3 ran end to end unmodified.**

## 2026-09-23 (digital pin substitution unconditionally offered, matching analog — a design reversal, made carefully)

User's explicit instruction, after discussing the Wiring Bench sandbox's own more-permissive digital handling: "i want that change to reflect real electronics in real life as user is a human they will be able to do anything so we shall be able to handle cases we just need to know which parts can use which pin we have parts in the beginning and we also have expected graph we can keep track of pins in a way that no conflict happens but we allow substitution where possible !! also implement that in code and research." This reverses an earlier decision this session (09-22, "domain pools generalized beyond the Uno") that a digital deviation was only ever *offered* when the lesson had genuine multi-component contention for a digital pin — a deliberately conservative gate, justified at the time by "the shown code must never silently drift from what's wired without an obvious reason." That justification stopped applying the moment `_adjusted_code` was built to always rewrite the shown code from `confirmed_pairs` ground truth, regardless of why a pin changed — the gate had quietly become pure caution with no remaining purpose, once the safety net around it existed.

**The infrastructure needed for this was already built and already domain-agnostic** — confirmed by reading each piece before touching anything: `_compute_pin_remap` (proactive reassignment when a step's own scripted target is already confirmed-claimed by a different component), `_reserved_pins` (every substitutable pin some *other*, not-yet-resolved step's own script wants), and `_adjusted_code` (its own docstring already said word-boundary matching was "required now that digital pins are substitutable too" — i.e., this exact scenario was anticipated and built for, just unreachable). The only actual gate was a `kind == "digital"` branch at the top of `_try_pin_substitution` that skipped straight to refusal unless `_reserved_pins` showed contention. Removed it. Digital and analog now go through the identical two-pass search: candidates excluding every pin some other step's own script still wants tried first (minimizes remap churn), then — only if nothing else works — those too (never a correctness requirement, since `_compute_pin_remap` reassigns the *other* component reactively the moment its own step finds its target taken; this is purely about avoiding unnecessary churn).

**The user's exact safety scenario — "if X can only get 8 and we give it to someone then we're screwed" — turned out to already be handled by a function that existed before today**: `_compute_pin_remap`, the one place the engine actually picks a pin autonomously (not just recognizes whatever the learner physically wired), already excludes every `_reserved_pins`-flagged pin, permanently, with no fallback — if every remaining free pin is reserved, it honestly reports exhaustion (`actual: None`) rather than silently colliding. `_try_pin_substitution`'s own two-pass ordering, it turns out, can't actually violate this in practice: since it only ever tests candidates against a *fixed* detected wiring (whatever the learner actually connected), there's structurally only one candidate that can ever pass — the loop order doesn't change *whether* substitution succeeds, only cosmetic preference. The real guarantee lives entirely in `_compute_pin_remap`, confirmed unit-tested directly (new: `test_compute_pin_remap_avoids_a_pin_a_third_components_future_step_wants`) and via the digital counterpart of the existing analog acceptance test (`test_digital_pin_substitution_accepts_a_pin_a_future_step_also_wants`).

**Fixing this surfaced two real, pre-existing engine bugs**, invisible until digital substitution was actually exercised through them for the first time:

1. `_supersede_scarce_leg_pairs` treated *any* new fact about a "scarce" component leg (a real component's own pin, e.g. `btn1:1.r`) as superseding an older one the moment the partner differed — correct for a genuine re-wire (the motivating case: a leg's Arduino-side pin moved from X to Y), wrong for a real multi-member net junction (a pull-down resistor sharing a pushbutton leg's own strip with the Arduino pin — two simultaneously-true facts, confirmed in two separate steps, not a rewire of one). Found via `digital-read-serial`'s real topology (`btn1:1.r` legitimately touches both `uno:2`/its substitute *and* `r1:1`) the moment a digital deviation on that exact leg finally became reachable. Fixed by requiring BOTH the old and every new partner to be board/connector-side (the same physical wire's endpoint, re-expressed or genuinely moved) before treating it as supersession — a partner that's a different component's own leg never evicts an existing fact, since that's an additional edge, not a replacement. This bug was actually *masking* a real short-circuit detection gap too: `test_exhaustive_digital_read_serial_variations.py`'s step-4 matrix had wrongly expected reusing the resistor's already-consumed leg (already tied to the pushbutton net from step-3) for a *second*, simultaneous connection to GND to be a harmless symmetric swap — it's a genuine short once step-3 has fixed which physical leg is which, and the engine now correctly refuses it. Test expectation corrected to match reality, not relaxed.

2. `_final_pin_for_component` walked `confirmed_pairs` one hop at a time, most-recent-first, but committed to the *first* hop found with no backtracking — correct for a simple linear chain, wrong the moment a scarce leg has two real, simultaneous neighbors (the same 3-way junction from bug 1) and the more-recent one happens to be a dead end (a component-to-component edge with nowhere further to go) rather than the one that actually leads to a board pin. Rewritten as a proper DFS: try each distinct neighbor most-recent-first, backtrack on a dead end instead of giving up — same "prefer the freshest route" bias as before, but no longer wrong when the freshest route doesn't pan out.

Full suite: 3,354 passed (2 new regression tests; several existing tests updated from "refused" to "accepted" expectations, since that's the actual, intentional behavior change — not relaxed, redesigned).

## 2026-09-23 (a real, more serious bug found via an 8-button diagram: chained substitutions could phantom-merge unrelated components at final_check)

Continuing the same-day stress-testing streak, a third user-supplied diagram (an 8-button digital piano + buzzer — 9 components sharing the Uno's 12-pin digital pool, leaving only 1 pin genuinely free) surfaced a real correctness bug, deeper than the previous two.

First, a genuine root-cause bug: `_compute_pin_remap` only checked `state["confirmed_pairs"]` (physically confirmed wiring) when picking a free pin for a not-yet-resolved component — never `state["pin_remaps"]`'s own list of pins already PROMISED to some OTHER component by an earlier, still-pending remap. With most of the domain pool already taken or reserved, several different components in a row could each independently see the SAME one leftover pin as "the" free choice, since none of them had been physically confirmed yet. Fixed by also excluding any pin already promised to a different component by an in-flight remap.

That fix alone wasn't sufficient. Deviating all 8 buttons at once, in a rotating chain (each button taking over the *next* button's scripted pin), corrupted `final_check`: several buttons got silently merged into one phantom shared net, a false "wrong" despite every individual step having been correctly accepted and `confirmed_pairs` being completely correct throughout. Root cause: `_apply_pin_remaps`/`_apply_pin_substitutions` resolved a pin by blanket string-replacing its OLD VALUE wherever that exact string appeared across the WHOLE pair list, one remap/substitution at a time, sequentially. ## 2026-09-22 (Q&A exploring pin-sharing semantics — one real finding, deliberately not fixed)

Working through, with concrete tests rather than assumptions, how the engine handles two components genuinely needing to share one point: confirmed real bus-sharing (I2C/SPI, already tested with real diagrams earlier this session) and component-to-component chaining (`led2:A` → `led1:A`, the same pattern Blink's own LED/resistor connection already uses) both work correctly — including dynamically, when the first component itself later deviates to a different pin (verified: `led2:A → led1:A` still passes with zero friction even after `led1` moves from A2 to A5).

This is deliberate design (`_pin_owner`'s own docstring: exists specifically so a substitution never "silently short two components onto the same physical Arduino pin instead of flagging a real conflict") — a domain pin is treated as exclusive by default, and genuine sharing must be explicitly authored (chaining, or the protocol-bus mechanism), not inferred from coincidental pin overlap.

**One real, newly-found asymmetry, deliberately left unfixed.** `checker.check` requires an EXACT net match (same set of pins, after connector-dropping) — not "these two are connected, plus possibly other things." This project already tolerates an analogous case for *landing* steps (the breadboard-bypass mechanism: wiring straight to the final pin instead of through the breadboard is explicitly accepted) — this same tolerance doesn't extend to a component-to-component wiring step.

**Deliberately not fixed, per direct user judgment call**: a learner sophisticated enough to independently choose this alternate (bypass-the-taught-method) wiring approach is already operating above what this app's guided, breadboard-centric teaching flow is actually for — not the target beginner path the lessons are built around. Documented here as a known, accepted limitation rather than a bug to chase, in case it's worth revisiting later.

## 2026-09-22 (1000-scenario stress suite finds a second, more serious instance of the same root-cause bug — fixed at the source this time)

User request: 1000 generated tests combining board-family switching, wrong/correct connection attempts, and deviations, checking final_check and generated code every time. Built `tests/test_board_translation_1000_scenarios.py`, same generated-parametrize style as the existing `test_sim_and_board_200.py` — 1000 individually-reported cases deriving (lesson, target board, behavior mode) deterministically from a seed, run against all 3 real lessons and their real code.ino files.

**A real design rule surfaced immediately, not a bug**: every real lesson has exactly one substitutable board pin, and — confirmed directly in `_try_pin_substitution`'s own docstring — digital-pin deviations are only ever accepted when the lesson has genuine multi-component contention for a digital pin somewhere; none of these three do, so an uncontended digital deviation is *correctly* refused every time (analog stays unconditionally free — an intentional, already-shipped asymmetry, not something to route around). The test's "deviate" mode had to become kind-aware: expect refusal-then-retry for digital, expect acceptance for analog.

**A second real, more serious bug, same root cause as the one found earlier this session.** ~30 of the first 45 generated cases failed at `final_check` for `analog-read-serial` specifically whenever the SIG leg deviated onto certain analog pins (reproduced concretely: A0→A5). Traced through `_run_check` → `_try_pin_substitution` → `_pin_owner`, and found `_pin_owner` has the *identical* structural flaw as the `_final_pin_for_component` bug fixed earlier today: it also called `checker.build_nets` over the full, un-deduplicated `confirmed_pairs` history. Direct instrumentation confirmed it: once `pot1:SIG` had been confirmed against both `uno:A0` (stale) and `uno:A5` (current), union-find — no notion of time — merged them into one net, and `_pin_owner` returned `"uno"` as the "owner" of `uno:A5` (having picked up the stale `uno:A0` half of the merged net and read the *board itself* off it, mistaking it for a rival component). `_try_pin_substitution` then wrongly refused to offer `A5` as a substitution target, since it looked already claimed by something else — even though the "something else" was the board, from a fact that had already been superseded, not a real second component.

This is worse than the first bug (which only corrupted generated code) because it can make the checker **actively refuse a fully correct final confirmation with no way to fix it** short of restarting the lesson.

**Fixed at the root this time, not per-reader**: added `engine._supersede_scarce_leg_pairs`, used at both `state["confirmed_pairs"]` write sites (`_run_check` and `_run_landing_check`, the latter newly given access to `board_component_ids` it didn't compute before). Defines "scarce" precisely — a real component's own leg, or a board pin that's a *substitutable* domain pin (13, A0) — as opposed to a shared-rail pin (GND/5V/3V3) or a connector/breadboard hole, which legitimately have many simultaneous, unrelated partners and must never evict each other. When a scarce pin's partner in newly-detected data differs from what an older `confirmed_pairs` entry says, the older entry is dropped; when it's simply being re-confirmed verbatim (e.g. a wiring check re-sending its own landing pair, which every existing test's exact-history assertions depend on), nothing is touched. First version of the fix was too aggressive — it dropped exact re-confirmations too, breaking 18 existing tests in `test_full_session_variations.py` that assert `confirmed_pairs`' precise historical shape — refined to only evict genuinely-superseded facts, which brought the full suite back to green. The earlier chain-walk fix to `_final_pin_for_component` was left in place as defense-in-depth (now redundant against clean data, but harmless).

**Result**: full suite (existing 2,346 + 1000 new + 1 coverage check) — **3,347 passed, 0 failed.**

Root cause: `engine._final_pin_for_component` (which `_adjusted_code` calls to figure out what a component's leg is *actually* wired to) built ONE flat net out of the ENTIRE session's `confirmed_pairs` history via `checker.build_nets`. Fixed by replacing the flat net-build with a most-recent-first chain walk through `confirmed_pairs` (reusing the exact "a newer fact about a pin supersedes an older one" principle `find_confirmed_pin` already used elsewhere in this file, generalized to follow a multi-hop chain — component leg → breadboard hole → Arduino pin — instead of a single direct pair, and never revisiting a pin once resolved). Verified the fix preserves the normal two-hop breadboard case (confirmed via the full existing suite, unchanged) while correctly resolving the exact scenario that broke: reversed-order search finds the LATEST confirmation first and returns immediately, never needing to consider the stale one at all.

## 2026-09-22 (per-board/per-part facts moved out of core logic into library JSON data, ahead of pre-building the full Wokwi catalog)

Prompted by the user directly: the growing pile of hardcoded per-board dicts (`BOARD_PIN_SHAPES`, `BOARD_PROTOCOL_PINS`, `RESERVED_PROTOCOL_LEGS` in `engine.py`; `BOARD_PIN_ALIAS_RULES`, `CONNECTOR_ONLY_TYPES` in `checker.py`) was about to become unmanageable once the library grows to cover Wokwi's full supported-hardware catalog (`docs.wokwi.com/getting-started/supported-hardware` — 60+ parts across 10+ microcontroller families: Uno/Nano/Mega, ATtiny85, 9 ESP32 variants, 3 STM32 variants, RPi Pico, plus sensors/displays/inputs/LEDs/motors/logic). Every one of those dicts encodes a fact about ONE specific board or part; the checker/engine algorithms themselves (net-folding, substitution search, domain-pool contention) never needed to know *which* board — they only ever needed *that* board's own declared shape. Decided this belongs in library JSON data, not core code, so the core stays generic and each new part just ships its own facts.

**New schema fields**, all additive to the existing card format (`TOOLS.md`/`PARTS.md`):
- `subtype` (new, alongside the pre-existing but never-actually-used-anywhere `type: "part"|"tool"` field — confirmed via grep before adding this, zero conflict risk): `"board"`, `"led"`, `"resistor"`, `"pushbutton"`, `"display"`, `"sensor"`, `"storage"`, `"breadboard"`, `"wire"`, `"cable"`, `"potentiometer"`, etc. Settled on this over a separate boards-only folder after weighing it directly with the user — one flat `library/parts/` stays simpler than sharding by category, and `subtype` gives the same classification power without a folder-structure decision baked in per part.
- On board cards only: `pin_domains` (`{"analog": [...], "digital": [...]}`, replaces `BOARD_PIN_SHAPES`), `protocol_pins` (`{leg: protocol_name}`, replaces `BOARD_PROTOCOL_PINS`).
- On any board or part card: `pin_aliases` (`{"mode": "prefix"|"strip", "prefixes": [...]}`, replaces `BOARD_PIN_ALIAS_RULES` — same shape, just per-card instead of centrally keyed by wokwi_type string).
- On any part card: `protocol_legs` (a list of the part's OWN bus-signal leg names, e.g. `["SCK","DO","DI"]` for the microSD card, `["SDA","SCL"]` for an I2C device) — replaces the single global `RESERVED_PROTOCOL_LEGS` name list. This is a real correctness improvement, not just a relocation: the old global list matched by NAME alone across every component in a diagram, so an unrelated part's own same-named leg (e.g. a photoresistor's `DO`) could in principle collide; the new per-part lookup only ever checks the actual component's own real wokwi_type card.
- `connector_only` (bool, replaces `CONNECTOR_ONLY_TYPES` set membership).

**Mechanical approach — lazy-default library loading.** Every touched function signature gained an optional `library=None` parameter, defaulting to `load_library()` internally when omitted. This meant the ~30 existing call sites across the test suite that never passed a `library` argument kept working completely unchanged, transparently picking up the real on-disk JSON. Added `functools.lru_cache(maxsize=1)` to `load_library()` since it's now called far more often (checker's alias/connector lookups default to it) — measured directly: 12.59s for the full suite without caching vs ~1s with it. Verified safe via grep: no test mutates the returned `Library` object or writes to a library JSON file mid-test.

**Board detection changed from a hardcoded string-prefix check to a schema-presence check**: `_board_card()` now asks "does this wokwi_type's library card declare `pin_domains`?" instead of `wokwi_type.startswith("wokwi-arduino-")`. This is deliberate, not incidental — it means a future ESP32/STM32/RPi Pico card is automatically recognized as a board the moment its own card declares `pin_domains`, with zero engine.py changes needed, which is the entire point ahead of the full-catalog buildout.

2. **`_adjusted_code`'s text substitution was a raw substring replace.** Safe for `"A2"` (a distinctive token) but not for a bare digit like `"5"` or `"13"`, which collide with unrelated numbers already in real lesson code (`Serial.begin(9600)`, `delay(1000)` next to `pinMode(13, ...)` in Blink). Trialed with a temporary patch first (per "discuss before editing"): full suite passed at 2,068/2,068 with zero test changes, and a real two-component end-to-end scenario (LED deviates onto the LCD's own scripted pin) correctly triggered accept-then-remap, including the `LiquidCrystal lcd(...)` multi-pin constructor surviving the boundary-safe regex fix untouched. User then raised a further edge case: what happens if the pin pool runs out entirely — some later step remapped so many times there's nowhere left to wire? Found this was a real, pre-existing ambiguity in `_compute_pin_remap` (not new to this session's digital work — the same gap already existed for analog's 6-pin pool, just harder to trigger): "no remap needed" and "remap needed but every pin is already taken" both returned a bare `None`, indistinguishable to the caller. ## 2026-09-21 (real bug: analog-pin substitution had no awareness of other components' pins)

User posed a scenario: LED wired to A1, a later step wants something else on A2, but what if the LED-A1 choice (or some other mix-up) ends up colliding with what step 2 needs? Verified empirically — a real gap, in two directions. ## 2026-09-21 (Wokwi↔library mapping: wokwi_type/wokwi_value added to PARTS.md)

### Two reference systems, and why they can't be merged
Raised and resolved: Wokwi's own ids (`led1`, `r1`, `bb1`) are instance-level — exactly right for `expected_nets`, since verification cares about *this specific component in this specific circuit*. Our library ids (`led`, `resistor-220`) are type-level — right for the gather phase and `tools_used`/`parts_used`, since the learner needs "get a 220Ω resistor," not "get r1." These can't be collapsed into one system; they need an explicit bridge.

### Rejected: a separate per-lesson mapping table
Considered a per-lesson `components: {"led1": "led", "r1": "resistor-220"}` block. Rejected in favor of something better: bake the Wokwi identity **into the library cards themselves** (`wokwi_type`, `wokwi_value`) so the mapping is authored once, globally, not once per lesson — removes an entire class of "lesson author forgot/mistyped the mapping" bugs.

### Verified real Wokwi type ids (not guessed)
- 📄 [wokwi-resistor reference](https://docs.wokwi.com/parts/wokwi-resistor) — confirmed attribute name `value`, a string in ohms (e.g. `"220"`, `"10000"`)
- Confirmed via search: `wokwi-arduino-uno`, `wokwi-breadboard`, `wokwi-led`, `wokwi-pushbutton`, `wokwi-potentiometer`

### The resistor ambiguity, and why `wokwi_value` exists
`wokwi-resistor` alone doesn't distinguish a 220Ω from a 10kΩ resistor — only `attrs.value` on the specific instance does. So `wokwi_type` alone is enough for most parts (LED, breadboard, pushbutton, potentiometer, the Uno itself), but resistors need a second field (`wokwi_value`) to disambiguate which library card a given instance maps to. This generalizes: any future part where Wokwi's type is shared across multiple real-world variants will need the same treatment.

### Not everything has a Wokwi identity
USB cable and jumper wires don't get a `wokwi_type` at all — a USB cable isn't simulated, and jumper wires are `connections`-array entries in Wokwi, not `parts`-array entries, so there's no component instance to map. Confirmed this is fine, not a gap: `wokwi_type` is optional, omitted where it doesn't apply. None of the Tier 1 tools (wire stripper, pliers, multimeter, etc.) get one either — Wokwi doesn't simulate hand tools at all.

## 2026-09-20 (key architecture split: pointing vs. verifying are two different problems)

Worked example that surfaced this: a lesson step says "connect the red wire to pin 13" — the system needs to (a) show the learner exactly where pin 13 is, and (b) later check whether they actually put the wire there. These turned out to be two genuinely different problems, one much easier than the other:

- **Pointing** ("show me where pin 13 is") — the target location is already known and fixed. Pin 13's physical position on an Arduino Uno is documented and identical on every Uno ever made. Once the geometry step has tracked the board (markers + homography, already planned), the system already knows where that point is in the current camera view — it just draws a highlight there. **Pure classical geometry/graphics, real-time, no LLM call needed at all.** This is not a detection problem — nothing is being discovered, a known template coordinate is just being transformed into the live camera's coordinate space.
- **Verifying** ("did the user actually put the wire there") — this is about detecting something new and unknown: wherever the learner's real wire actually ended up. That's the hard, unsolved half — the actual research (grid-augmented VLM grounding) is needed here, not for pointing.

**Practical implication — this de-risks the build timeline**: the "pointing" half of the AR experience isn't blocked on the research succeeding at all. It can be built and demoed early using only the geometry/tracking pipeline (Category A, already-existing tools), giving a working, visually convincing AR experience well before the harder verification research (Category B) is proven out. The two capabilities should be built and evaluated on separate tracks.

### Revised: it's actually three capabilities, not two
Follow-up scenario raised: what if the required components are just loose on a table, not yet placed? Their positions aren't known in advance — a red wire could be anywhere, in any orientation — so this isn't a geometry problem like pointing to pin 13 is. It's a genuine object-identification problem, and reveals a third, distinct capability:

1. **Identify loose objects** ("which one's the resistor, roughly where is it on the table") — a semantic recognition task, not a precision task. VLMs are actually good at this (the spatial-blindspot finding is specifically about *exact coordinates*, not "what is this thing"). Well-trodden ground — prior art already found: Roboflow's resistor-detection dataset, the PMC electronic-parts-classification paper. Does **not** need the novel research.
2. **Point to a known board location** (pin/output N) — pure geometry once the board is tracked. No AI needed at all.
3. **Verify the actual connection** (did the wire really end up there) — the hard, unsolved precision-grounding problem. This is the actual research contribution — nothing else in this list is.

Only #3 is genuinely novel/risky; #1 and #2 are both solvable with existing techniques and could be built and demoed well before the research is proven out.

### UX shape this implies: wide → close, two phases
Storyboarded through: **Phase A (wide shot, gathering)** — camera sees the cluttered table, system identifies and circles/highlights what's needed for this step (capability #1) — "there's your board, there's the red wire, there's the tool." **Phase B (close-up, working)** — learner physically gathers the circled items and brings them together near the camera to actually connect them — now capabilities #2 (point to the exact pin) and #3 (verify the connection) take over. The transition from wide to close view is itself a usable signal for switching system modes — no separate detector needed for "which phase are we in."

## 2026-09-20 (system architecture: multi-model, call frequency, local vs. server)

### Q1: Do we use multiple models, or different models for different parts of a lesson?
Two separate concerns, and — per follow-up — two separate *routing philosophies* within "production":
- **Research phase**: yes — benchmark multiple candidate models (Claude, GPT-4/5-class, Gemini) against the same grid-overlay test set, **per sub-skill** (reading grid labels, reasoning about expected wiring, writing feedback) rather than one overall accuracy number. This extends the "baseline comparison" step already in the research plan (step 4).
- **Production, lever A — cost-cascading**: cheap/fast model handles the easy, common checks; escalate to a stronger/pricier model (or a human specialist) only when the cheap model isn't confident. Cuts cost 45–85% while keeping ~95% of quality in production systems using this pattern. Optimizes for cost.
  - 📄 [arXiv: Cluster, Route, Escalate — Cascaded Framework for Cost-Aware LLM Serving](https://arxiv.org/pdf/2606.27457)
  - 🔍 [LLM Routing and Model Cascades: How to Cut AI Costs Without Sacrificing Quality](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades)
- **Production, lever B — task-based/capability routing** (raised as the more natural fit for us): route each *kind* of question to whichever model is empirically best at that specific sub-skill, independent of price — not a cost ladder at all. Real deployments do exactly this: product-search queries to one model for speed, customer complaints to another for tone/nuance, fraud analysis to a third for multi-step reasoning.
  - 🔍 [Task-Based LLM Routing: Optimizing LLM Performance for the Right Job](https://portkey.ai/blog/task-based-llm-routing/)
  - 📄 RouteLLM (UC Berkeley, ICLR 2025) — 85%+ cost reduction while keeping ~95% of GPT-4-level performance, sending only 14% of queries to the strong model
- **Combined fallback rule**: on low confidence, reroute to "the model that's actually good at this sub-task" (task-based) rather than automatically "a bigger/pricier model" (cost-based) — human specialist is the last resort if nothing is confident.
- **Implication for the product**: the AI tier's uncertainty threshold becomes the natural trigger for offering to escalate to a human specialist tutor — ties the routing pattern directly to the tiering model already decided.

### Q2: Is the grid overlay/geometry step used constantly, or only for specific steps?
Split into two different-cost operations, running on different schedules:
- **Geometry/tracking (finding the board, keeping the grid aligned)** — cheap classical CV math, runs continuously, every frame, like any standard AR overlay tracking.
- **LLM reasoning call ("is this wired correctly")** — slow (seconds) and costs money per call — should NOT fire every frame. Triggered only at checkpoints: user finishes a step and requests a check, camera holds still (implying they've stopped adjusting), or a lesson-defined milestone.

### Q3: Local or server?
Hybrid — this is the standard architecture for this class of app, not something to invent:
- **On-device (local)**: geometry/tracking/overlay rendering. AR overlays lagging more than ~100ms feel visibly broken to a person, tighter than a network round-trip can reliably guarantee.
- **Server/cloud (API)**: the actual multimodal LLM call (Claude). Frontier models aren't run on a phone; since the call only fires occasionally (per Q2), a 1–3s round trip is fine.
- Real-world precedent for exactly this split: Apple Intelligence routes between on-device models and cloud compute; Google's Gemini Nano runs on-device but escalates harder requests to cloud Gemini.
- 📄 [Edge Assisted Real-time Object Detection for Mobile Augmented Reality (WINLAB/Rutgers)](https://www.winlab.rutgers.edu/~luyang/papers/mobicom19_augmented_reality.pdf)
- 🔍 [Hybrid Cloud-Edge LLM Inference: When On-Device Models Beat the Cloud](https://tianpan.co/blog/2026/04/10/hybrid-cloud-edge-llm-inference-when-to-run-on-device)

### Resulting architecture decision
Local: continuous geometric tracking + grid rendering (OpenCV, on-device). Cloud: occasional, checkpoint-triggered multimodal LLM calls, routed cheap-first with escalation to a stronger model or a human specialist when confidence is low. Not decided yet: exact confidence-threshold mechanics for escalation, and which "cheap" vs. "strong" models to pair for the cascade (needs the model-benchmarking research to inform this).

## 2026-09-20 (★★★ FINAL PROJECT DEFINITION — what's engineering vs. what's research)

### The final idea, one paragraph
A platform that teaches real, hands-on skills (starting with Arduino/electrical circuits) by watching the learner through a camera and giving live, corrective guidance — either from a human specialist (premium tier) or an AI tutor (cheaper tier). The AI tutor is the platform's core differentiator and the final-year project's research contribution: it combines classical geometric computer vision with a multimodal LLM to precisely identify which exact breadboard hole/Arduino pin a component is connected to — something no existing product or published system does today for this domain.

---

### ✅ CATEGORY A — Build with existing, off-the-shelf tools (engineering, not research)
These are solved problems; use proven libraries/services rather than reinventing them, so project time goes toward the actual research contribution.

| Feature | Existing tool/approach to use |
|---|---|
| Marker detection (breadboard/board corners) | OpenCV's built-in ArUco marker detection — mature, off-the-shelf |
| Homography / grid mapping from markers | OpenCV standard geometry functions — well-established, no research needed |
| The "brain" doing semantic reasoning over the grid-annotated image | Claude (or another frontier multimodal LLM) via API — used as-is, not trained/fine-tuned |
| AI chat assistant for quick questions | Same LLM API, prompted with session/lesson context (RAG-lite: stuff the current lesson state into the prompt) |
| Secure/encrypted specialist↔user channel | Existing secure protocol — TLS, or WebRTC's built-in DTLS-SRTP for live video. **Never hand-roll cryptography.** |
| Performance/mistake logging | Standard application logging + basic stats (accuracy over time, error-type breakdown) — software engineering, not novel research, but still required for the dissertation's evaluation chapter |
| Tool-selection verification (stretch goal) | Same object-detection/VLM pipeline as the core system, just pointed at a tool instead of a wire — reuse, don't rebuild |

### 🔬 CATEGORY B — The actual research (this IS the final-year project's contribution)
**Central question to research and answer: can a geometry-preprocessed image + a general-purpose multimodal LLM reliably identify the exact breadboard hole / Arduino pin a wire or component is connected to — accurately and consistently enough to power a real AI tutor?**

This is genuinely unsolved (confirmed: SmartBreadboard-3D's detection module is an unbuilt stub; the Roboflow project only does plain object detection, not grid-grounded hole identification; published VLM research — [Spatial Blindspot of VLMs](https://arxiv.org/pdf/2601.09954) — confirms raw multimodal LLMs are unreliable at this without help). What needs actual experimentation:
- How to best generate and render the grid overlay (line thickness, transparency, labeling scheme) for maximum LLM accuracy — draws on [Grid-augmented vision](https://arxiv.org/pdf/2411.18270) and [Visual Position Prompt](https://arxiv.org/pdf/2503.15426) as starting points, but needs to be adapted and tuned specifically for breadboard/Arduino imagery
- How much domain documentation/context to feed the LLM alongside the image (breadboard conventions, current lesson's expected circuit) to maximize correctness
- Measuring real accuracy: build a test set of real breadboard photos with ground-truth wiring, run the pipeline, measure hole-identification accuracy, error patterns, and where it fails
- Comparing this approach against baselines (e.g., raw LLM with no grid, or a custom-trained small object detector) to justify the architecture choice with data, not just intuition
- Deciding the safe scope boundary: one board (Arduino Uno), one/few lesson types — and documenting how the accuracy holds up or degrades as complexity increases

**This is the part of the dissertation that is a genuine, original contribution** — everything in Category A is "we used the right existing tool for a solved problem"; Category B is "we designed, built, and evaluated a new pipeline for a problem nobody has published a working solution to."

### 🕓 Deferred / future work (not built now, mentioned in dissertation as future direction)
- General object recognition → pull up manuals for *any* machine (scoped now to just the one board/domain instead)
- General appliance danger/safety detection across arbitrary device types (Arduino/breadboard is low-voltage DC, so lower real safety risk than mains appliances anyway — natural reason to defer this)

### Generalizability check: does the core technique transfer beyond breadboards? (e.g. car repair)
- **Transfers directly**: any flat, gridded, standardized structure — e.g. a car's **fuse box / relay panel** is almost the same geometric problem as a breadboard (flat, regular grid, known layout per model). Same pipeline (marker/corner detection → homography → grid overlay → LLM) applies with minimal adaptation.
- **Does not transfer directly**: a full 3D engine bay — irregular, occluded, no single flat plane, no fixed template across car models. That's a different problem (plain object/part recognition, which VLMs already handle reasonably via semantic knowledge) rather than the precise coordinate-grounding trick.
- **Market reality check** — car repair AI is already mature/crowded, unlike breadboards: 🏢 [ARI: AI Wiring Diagram Assistant](https://ari.app/2026/05/introducing-aris-ai-wiring-diagrams/), 🏢 [MECH AI](https://mechai.app/), 🏢 [Fixomotive Repair](https://fixomotive.in/repair), 🏢 [Identifix wiring diagrams](https://www.identifix.com/wiring-diagrams/) — all generate wiring diagrams/fuse data by make/model/year already. None do live-camera geometric grounding on the physical part in front of the user (they show a diagram to read, not AR-overlaid live verification) — so the technique would still differentiate, but this is a funded, populated market, unlike the empty breadboard/Arduino space.
- **Conclusion**: good validation the core research generalizes (worth a "future work" line in the dissertation), but confirms breadboard/Arduino remains the right FYP domain — it's the one place this exact technique has zero competition.

## 2026-09-20 (Architecture validated: grid-augmented VLM grounding for exact hole/pin ID)

### Question raised
Is it true that no current AI model — not even a frontier multimodal LLM like Claude — can reliably identify the exact breadboard hole/Arduino pin from an image? And could a Claude-class model + strong domain documentation + geometric preprocessing solve it?

### Findings — both parts confirmed by real research
**Part 1 — yes, this is a documented, real limitation of VLMs (including the Claude/GPT-4V/Gemini class), not just something nobody tried:**
- 📄 [arXiv: The Spatial Blindspot of Vision-Language Models](https://arxiv.org/pdf/2601.09954) — dedicated paper on this exact weakness
- 📄 [arXiv: ViewSpatial-Bench — Evaluating Multi-perspective Spatial Localization in VLMs](https://arxiv.org/abs/2505.21500)
- 📄 [arXiv: From Pixels to Places — geolocalization benchmark](https://arxiv.org/html/2508.01608v1) — general finding: VLMs "lack the reliability required for fine-grained or high-precision localization tasks compared to classical [geometric] methods"

**Part 2 — the proposed fix (VLM + geometric preprocessing/documentation) is a real, published, named technique, not something to invent from scratch:**
- 📄 [arXiv: Grid-augmented vision — simple yet effective approach for enhanced spatial understanding in multimodal agents](https://arxiv.org/pdf/2411.18270) — overlays a grid onto the image before feeding to the model; converts a hard coordinate-regression problem into an easy "which cell" classification problem
- 📄 [arXiv: Visual Position Prompt for MLLM based Visual Grounding](https://arxiv.org/pdf/2503.15426) — same family, structured spatial cues burned into the image
- General research finding: "external scaffolding — adding annotations, grids, or partitions to the input image — consistently improves model performance" on spatial/counting/description tasks

### ⭐ CORE ARCHITECTURE — central contribution of the whole project
> So the real architecture for your FYP is: homography/marker-based grid detection (classical CV, deterministic) → burn that grid visibly onto the image → feed to a multimodal LLM with strong domain documentation about breadboard/Arduino layout → ask it "which labeled cell is this wire in." You're not fighting the model's weakness, you're using classical geometry to hand it exactly the crutch this published research shows works. And since nobody's applied this specifically to breadboards/Arduino (SmartBreadboard-3D never finished its detection module; the Roboflow project does plain object detection, not this grid+VLM grounding approach), applying and evaluating it for this domain is a genuinely original contribution.

**This is the spine of the dissertation — everything else (chat assistant, tool recognition, safety detection, etc.) is a secondary feature built on top of this core pipeline, not a replacement for it.**

### Resulting architecture for the FYP AI-tutor component
1. Detect breadboard/Arduino board corners (via ArUco markers, per earlier decision) → classical CV, deterministic
2. Compute homography → derive the known grid (breadboard hole rows/columns, or Arduino pin template for the fixed board model, e.g. Uno)
3. **Burn that grid visibly onto the image** (labeled cells/rows) — this is the "geometric preprocessing" step
4. Feed the grid-annotated image + strong domain documentation (breadboard/Arduino layout conventions, lesson-specific expected wiring) to a multimodal LLM (Claude) as the reasoning/semantic layer
5. Ask it to identify component placement and wiring against the expected circuit for the current lesson, generate feedback

### Why this matters for the project
- Confirms genuine novelty: nobody has applied this "grid-augmented VLM grounding" technique to breadboards/Arduino specifically (checked — SmartBreadboard-3D's detection module is an unbuilt stub; Roboflow's resistor-detection project uses plain object detection, not this approach).
- De-risks the FYP significantly: no need to train a custom object detector from scratch or collect a large labeled dataset — leverages an existing frontier multimodal model (Claude) for the semantic/component-recognition part, while the hard geometric grounding is handled by classical, well-understood CV (homography), not by trying to force the LLM to do something the literature says it's bad at.
- Gives a clean, citable methodology section for a dissertation: apply + evaluate a published spatial-grounding technique (grid-augmented VLM prompting) in a novel domain (breadboard/Arduino circuit verification for AR-guided tutoring).

## 2026-09-20 (Final Year Project scoping: which AI piece to actually build)

### Context
This platform is the user's final year project, which requires a data-science/ML component. Two candidate AI features identified:
1. **"AI instead of tutor"** — AI vision system fully replaces a human specialist for guidance (the core differentiator of the business idea).
2. **"AI assists the specialist"** — AI copilot that helps a human tutor identify tools/components/steps, human stays in the loop as final authority.

### Key technical sub-question: can we identify the exact breadboard hole / Arduino pin the user should connect to?
**Yes — and it's more tractable than expected**, because a breadboard/Arduino board is a known, fixed grid, not an arbitrary scene:
1. Detect board corners (via edge detection, or much more reliably via printed ArUco/fiducial markers at the corners)
2. Compute a homography from the detected corners
3. Map any point in the camera frame to an exact row/column hole using the breadboard's known standard grid spacing — no need to ML-detect every individual hole
4. Same approach for Arduino pin headers: fix the target board to one known model (e.g. Arduino Uno) for v1, detect board outline/orientation, overlay the known/documented pin-position template

**Feasibility check:** searched for existing implementations — [SmartBreadboard-3D (GitHub)](https://github.com/sasivaradhansbee25-hue/SmartBreadboard-3D) attempts exactly this (breadboard detection + 3D visualization) but its own README confirms the actual hole-detection CV module is still an unbuilt stub ("Phase 9+"). **Nobody has shipped this specific piece yet** — confirms it's a real, well-scoped, unsolved technical problem (good for a FYP contribution), not something to build from an existing library.
- Other prior art found on component-level detection (not hole-level): [Roboflow: Resistor Detection dataset/model](https://universe.roboflow.com/circuits-project/resistor-detection-5azes) — explicit goal "take a picture of breadboard, circuit auto-simulated, tells you if it's safe/fully connected" — same vision, same unsolved-at-scale problem.
- [PMC: Vision-Based Detection and Classification of Used Electronic Parts](https://pmc.ncbi.nlm.nih.gov/articles/PMC9738186/) — academic precedent for component classification (1,734-image dataset, capacitor/potentiometer/regulator), useful methodology reference even though not breadboard-hole-specific.

### Recommendation / decision
Go with **Option 1 (AI instead of tutor), tightly scoped**: one board (Arduino Uno only for v1), one starter lesson (e.g. LED + resistor), full pipeline = corner/marker detection → homography → grid-position mapping → component detection → wiring correctness check → feedback. This is harder-sounding but the core hard part (exact hole ID) decomposes into a well-defined, solvable geometry + CV problem rather than an open-ended one. It also doubles as both the FYP's data-science contribution AND the platform's core product differentiator — stronger than Option 2 (AI-assists-human), which would build most of the same underlying tech without it standing alone as a complete system.

### Next steps
- Decide: markers (ArUco stickers on breadboard corners) for v1 reliability, vs. pure corner/edge detection (harder, more "impressive" but riskier) — markers strongly recommended for a FYP timeline.
- Scope exact v1 lesson + success criteria (e.g. "detect LED + resistor correctly placed across specific breadboard rows, powered from Arduino digital pin 13") before writing any code.
- Look into whether to train a custom object detector (YOLO-style) for components (LED, resistor, wires, Arduino board) vs. use an existing pretrained model + fine-tune — dataset size/collection effort needs its own research pass.

- Need to evaluate: cost, availability, SDK/API access for building a custom app on each of these before picking a hardware target. Also worth considering a **phone-AR MVP first** (skip glasses hardware risk entirely) before committing to a specific glasses platform.
